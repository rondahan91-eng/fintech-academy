# ביקורת על קובץ העיצוב

מול `design/system/DESIGN.md`, `tokens.json` ו-`layout.md`, ומול המוקאפ שצירפת.

**הקובץ קלט נכון הרבה מאוד** — שלוש העמודות ו-360/296, הקיפול ב-1140, ידית הגרירה, נקודה במקום צ׳יפ בטבלה צפופה, קו שיער כל חמש שורות, איסור ההילה מאחורי האווטאר, שתי צורות שורת הכשל, והכלל שהמספרים חייבים להסתדר. **גם המוקאפ מיישם אותם.**

**שבעה פערים. שלושת הראשונים משנים התנהגות.**

---

## 1 · אין מצב `pending` — ולכן בדיקה שנכשלה אדומה

זה נראה במוקאפ: `✕ הנטו אינו נכון` באדום.

`tokens.json` מגדיר את זה אחרת, ובמפורש:

> **בדיקה טרם עברה. נייטרלי חם בכוונה ולא אדום** — תלמיד יריץ 15 פעם לפני שיעבור, **וזה המצב הרגיל ולא שגיאה.**

**קובץ העיצוב מכיר ארבעה צבעים סמנטיים** — ירוק לחיובי, אדום ל"שגיאות", זהב לאזהרה, אפור למשני. **אין בו את הנייטרלי החם**, ולכן כשל נופל אוטומטית על אדום.

**מה להוסיף:**

```
Working Sand (#F4EBE4 / דיו #7A6A5E) — בדיקה שטרם עברה.
לא אדום. זהו המצב הרגיל של עבודה בתהליך.
```

**זה לא ניואנס.** תלמיד רואה את המסך הזה ארבעים פעם בשבוע. **אדום ארבעים פעם מלמד אותו שהוא נכשל כל הזמן.**

## 2 · אין מצב `breach` — והאדום מבוזבז על באגים

במערכת שלנו האדום שמור **להפרה אתית בלבד**: מכירה שפוגעת בלקוח, שירוט, ניסיון חוזר לחלץ פתרון מאלעד.

> **הצבע היחיד במערכת שמזהיר, ולעולם לא על באג.**

בקובץ העיצוב `Alert Red` מוגדר ל"ערכים שליליים, הפסדים, **שגיאות**, פעולות הרסניות". **ברגע שהוא על כל טסט שנכשל, לא נשאר לו כוח למודול האתיקה** — שהוא הרכיב שבשבילו הצבע הוגדר.

**מה לשנות:** `Alert Red` נשאר לערכים שליליים בכסף (מוסכמת פיננסים, נכון), **ומתווסף צבע רביעי להפרה** — או שהאדום נשמר לה בלעדית והכסף השלילי מסומן בסימן מינוס ובמונוספייס, בלי צבע.

## 3 · אין עברית בקובץ, ו"tight tracking" הוא ההפך מהכלל שלנו

הקובץ אומר *"Display / Hero: Weight 700, **tight tracking**"*.

`DESIGN.md` קובע הפוך, אחרי בדיקה:

> **מרווח אותיות אפס לאורך כל הסולם. בעברית מרווח שלילי פוגע** — הוא מדביק אותיות סופיות ומטשטש את ההבחנה ביניהן.

**ושלושה כללים נוספים נעדרים לגמרי:**

| | |
|---|---|
| **RTL** | כל הממשק עברית. הקובץ לא מזכיר כיווניות אף פעם |
| **איי LTR** | קוד ופלט נשארים משמאל לימין **בתוך** טקסט עברי — `unicode-bidi: embed`. זו נקודת כשל ידועה, והיא קורית בכל מסך |
| **גופנים מקומיים** | סביבה סגורה, **אין CDN.** "use any modern sans-serif" אינו מספיק — הוא חייב לתמוך בעברית **ובניקוד**, ולהיות מוגש מהשרת |

**התוספת:** גופן UI עם תמיכה מלאה בעברית (Assistant / Heebo), `letter-spacing: 0` בכל המדרגות, ו-Consolas לקוד — **כי הוא קיים בכל מכונת Windows בבית הספר, אפס הורדה.**

## 4 · `max-width: 1280px` סותר את הנוסחה שבקובץ עצמו

הקובץ קובע שני דברים שאינם יכולים להתקיים יחד:

```
Layout:  Max-width containment: 1280px centered
Layout:  code editor (flexible = screen width − 720px)
```

**על מסך 1366:**

| | עורך |
|---|---|
| הנוסחה על רוחב המסך | **646px** |
| הנוסחה על 1280 | **560px** |

**86 פיקסלים, שהם כ-4 תווים בשורת קוד.** ו-`layout.md` §1 קובע ש-500px הוא הרצפה הנוחה — **1280 מכניס את מסך היעד לטווח שהוגדר כמינימום.**

**מה לשנות:** להצהיר ש-`max-width` **אינו חל על מסכי האפליקציה.** הם משתמשים ברוחב המסך המלא פחות ריפוד, ומחשבים את השוליים בעצמם — כפי שמסך הציונים (1172 + 97×2) ומסך התלוש (1132 + 117×2) כבר עושים.

## 5 · כללי דף נחיתה שנכנסו למוצר שאין בו דף נחיתה

שלושה סעיפים בקובץ מתייחסים למשהו שלא קיים:

```
Section vertical gaps: clamp(4rem, 8vw, 8rem)
Lesson / marketing sections: Zig-zag alternating rows
Body: max 72ch per line
```

**אין במערכת אף מסך שיווקי.** חמישה מסכים, כולם 1366×768, וכולם עם תקציב אנכי מלא.

**ומרווח סקשן אחד של 128px הוא 19% מכל התקציב.** שניים — 37%. הקובץ עצמו אומר, שני סעיפים למטה:

> **Vertical budget:** Treat height as the tighter constraint... **no slack.**

**שני הכללים סותרים זה את זה בפער של פי עשרה.** למחוק את השלושה, או לסמן אותם `לא בשימוש — אין מסכי שיווק`.

*(ו-72ch לא רלוונטי לאף עמודה: הרחבה ביותר היא 720px.)*

## 6 · הסטגר עולה 1.8 שניות במסך שנסרק בשלוש דקות

```
Staggered cascades for lists/tables: 60ms between items
```

**מסך המורה הוא 30 שורות:**

```
30 × 60ms  =  1.8 שניות עד שהשורה האחרונה מופיעה
+ 380ms    =  2.18 שניות לתמונה מלאה
```

**זה מסך טריאז'.** המורה נכנס בין שיעורים כדי לראות מי צריך אותו — **ומחכה שתי שניות לרשימה.**

**מה לשנות:** תקרה על הסטגר — `min(60ms × index, 300ms)` — או **אין סטגר בטבלאות נתונים בכלל.** הסטגר יפה לרשימת כרטיסים; **בטבלה של 30 שורות הוא מאט עבודה.**

## 7 · חסרים מספרי החיתוך של האווטאר

הקובץ אומר *"Full-bleed avatar art with a 48px fade, fixed width and height"* — **בלי המספרים.**

הם קיימים, והם משמעותיים כי **אחד מהם הוא נכס שצריך לייצר:**

| מסך | מסגור |
|---|---|
| שיחת הקליטה | **420×520** — הנכס הקיים, ללא הקטנה |
| פאנל מסך העבודה | **240px גובה — חיתוך ייעודי חדש, ראש וחצי גוף** |

**זה לא ניסוח מחדש של הקיים.** ברוחב 296 המסגור המלא נותן 366px גובה ומוציא את הפאנל מהמסך ב-126 פיקסלים. **הקטנה לא תעבוד — צריך חיתוך.**

## מה שהמוקאפ עשה נכון ושווה לציין

| | |
|---|---|
| **`שכר · עד 800 ₪`** | תואם SPEC §3.2. **תיקן מוקאפ קודם שכתב 1,250** |
| **`בדיקות גלויות · 4`** | ארבע ולא 15 — הספירה הנכונה |
| **שתי צורות הכשל** | השוואה (`התקבל 4,710 · צפוי 4,890`) והסבר (`אין כותרת ליד כל מספר`) — **בדיוק שתי הצורות** |
| **`פריטי השבוע 🔒 נפתח לאחר ההגשה`** | גיטינג הפנסיה, כפי שנקבע |
| **`פישוט. המס האמיתי — שבוע 13`** | השורה בעמודת המשימה, מילה במילה |
| **החשבון** | 6000 × 0.18 = 1,080; 6000 − 1,080 − 210 = **4,710**, וצפוי **4,890**. **הבאג המודגם נכון עד השקל** |

**וגם ידית הגרירה נראית כידית ולא כקו** — הפריט שביקשתי במפורש שלא ייבנה כגבול.
